# Transaction Anomaly Detection Using Unsupervised Learning

**AI Engineering Project — Group 1**
Unsupervised anomaly detection on the IBM Credit Card Transactions dataset, built as a production-style engineering project rather than a single notebook.

---

## 1. Project Overview

Financial institutions must flag suspicious card transactions in near real time, but labeled fraud examples are scarce, expensive to obtain, and quickly go stale as fraud patterns evolve. This project builds a complete **unsupervised** anomaly-detection pipeline — data ingestion, validation, preprocessing, behavioral feature engineering, model training, evaluation, explainability, and an interactive dashboard — that identifies suspicious transactions **without using fraud labels during training**.

The `Is Fraud?` column present in the source data is deliberately excluded from every feature used for training and is reserved exclusively for **post-hoc evaluation**: it lets us report legitimate, honest metrics (ROC-AUC, average precision, precision/recall@k) for how well each unsupervised model's anomaly ranking agrees with real fraud outcomes, without ever leaking that signal into the models themselves.

## 2. Problem Statement

Given a stream of card transactions described by amount, merchant, timing, and channel (chip/swipe/online), rank each transaction by how anomalous its *behavioral context* is relative to that customer's and that merchant's typical activity — with no fraud labels available at training time. High-ranked transactions are surfaced to a fraud analyst for review.

**Business motivation:** unsupervised anomaly detection is production-relevant because (a) new fraud patterns emerge before they're labeled, (b) label collection lags real transactions by weeks, and (c) a behavior-based anomaly score generalizes to fraud types never seen in historical labels — complementing, not replacing, supervised fraud models.

## 3. Dataset

- **Source:** [IBM / Kaggle — Credit Card Transactions](https://www.kaggle.com/datasets/ealtman2019/credit-card-transactions) (`ealtman2019/credit-card-transactions`), a synthetic transaction dataset generated by IBM's multi-agent virtual-world simulator (also used in the IBM TabFormer research).
- **Scale:** ~24 million transactions across ~2,000 synthetic users. The pipeline supports both a **stratified sample** (default, `sample_frac` in `configs/config.yaml`, sampled by `User` to preserve per-customer behavioral history) for fast iteration on commodity hardware, and the **full dataset** for a final production run.
- **Raw schema:**

| Column | Description |
|---|---|
| `User`, `Card` | Synthetic customer / card identifiers |
| `Year`, `Month`, `Day`, `Time` | Transaction date and time components |
| `Amount` | Transaction amount (USD, as string with `$`, cleaned in preprocessing) |
| `Use Chip` | Channel: Chip Transaction / Swipe Transaction / Online Transaction |
| `Merchant Name` | Anonymized merchant identifier |
| `Merchant City`, `Merchant State`, `Zip` | Merchant location |
| `MCC` | Merchant Category Code |
| `Errors?` | Transaction error flags (e.g. Insufficient Balance, Bad PIN) |
| `Is Fraud?` | Ground-truth fraud label — **held out of training, used only for evaluation** |

See `notebooks/01_data_understanding.ipynb` for the full per-feature profiling (dtypes, cardinality, missingness) and `reports/eda/` for generated visualizations.

**Known limitations:** the data is synthetic, so fraud patterns reflect the simulator's generative rules rather than real-world adversarial behavior; `Merchant State`/`Zip` are missing for online transactions by construction; and severe class imbalance (~0.1–0.2% fraud) means evaluation must rely on ranking metrics (ROC-AUC, average precision, precision@k) rather than accuracy.

## 4. Methodology

```
Raw CSV → Validation → Preprocessing → Feature Engineering → Train/Val/Test Split
        → Model Training (4 unsupervised models) → Evaluation & Comparison
        → Explainability → Streamlit Dashboard / Batch Prediction
```

1. **Validation** (`src/data/validator.py`) checks schema, dtypes, and value ranges before anything downstream trusts the data.
2. **Preprocessing** (`src/data/preprocessing.py`) cleans the `Amount` field, imputes missing values, removes duplicates, winsorizes extreme outliers, frequency-encodes high-cardinality categoricals, and scales numeric features — all inside a `ColumnTransformer`-based `sklearn` `Pipeline` that is fit once and persisted (`models/scaler.pkl`) for consistent inference.
3. **Feature engineering** (`src/features/feature_engineering.py`) derives 14 behavioral features (customer spending profile, merchant frequency, time-based patterns, rolling/velocity statistics) — well above the 6-feature minimum.
4. **Modeling** (`src/models/`) trains **Isolation Forest, Local Outlier Factor, One-Class SVM, and a PyTorch Autoencoder**, each wrapped in a common `BaseAnomalyModel` interface with `fit` / `predict` / `score_samples` / `save` / `load`, orchestrated by `src/pipeline.py`.
5. **Evaluation** (`src/evaluation/`) compares all models on runtime, ranking quality against the held-out fraud label, and business-relevant precision@k.
6. **Explainability** (`src/explainability/explain.py`) surfaces per-transaction anomaly score breakdowns, permutation feature importance, and (for the Autoencoder) per-feature reconstruction error.
7. **Dashboard** (`dashboard/`) is a multi-page Streamlit app for EDA, model comparison, and live scoring of uploaded transactions.

## 5. Feature Engineering

| Feature | Description |
|---|---|
| `customer_avg_amount` | Mean transaction amount for the customer (expanding, causal) |
| `customer_max_amount` | Max transaction amount seen so far for the customer |
| `customer_txn_count` | Running count of the customer's transactions |
| `merchant_txn_frequency` | How often this merchant appears in the dataset |
| `avg_daily_spending` | Customer's average spend per active day |
| `weekend_indicator` | 1 if the transaction occurred on Sat/Sun |
| `business_hour_indicator` | 1 if the transaction occurred within configured business hours |
| `time_since_prev_txn` | Minutes since the customer's previous transaction |
| `rolling_avg_amount` | Rolling mean of the last N transaction amounts for the customer |
| `transaction_velocity` | Count of the customer's transactions in the trailing window |
| `merchant_diversity` | Number of distinct merchants the customer has used so far |
| `customer_activity_frequency` | Transactions per active day for the customer |
| `amount_deviation_from_customer_mean` | (Amount − customer_avg_amount) / customer_std_amount |
| `amount_zscore_by_merchant` | Amount z-scored against that merchant's global distribution |

All customer-level rolling/expanding statistics are computed **causally** (using only prior transactions, via `groupby().shift()` / `expanding()`) to avoid target leakage and to match how the model would score transactions in production.

## 6. Models

| Model | Why chosen | Key hyperparameters |
|---|---|---|
| **Isolation Forest** | Fast, scales to millions of rows, no distance computation, handles mixed-scale features well | `n_estimators`, `max_samples`, `contamination` |
| **Local Outlier Factor** (novelty mode) | Captures *local* density anomalies that global methods miss (e.g. a mid-size transaction anomalous only for a low-spend customer) | `n_neighbors`, `contamination` |
| **One-Class SVM** | Learns a flexible non-linear decision boundary around normal behavior via the RBF kernel | `nu`, `gamma`; trained on a stratified subsample for tractability (documented trade-off) |
| **Autoencoder** (PyTorch) | Learns a compressed, non-linear representation of "normal" transactions; reconstruction error is a natural anomaly score for complex feature interactions | layer sizes, `learning_rate`, early stopping |

All hyperparameters live in `configs/model_config.yaml`, including optional randomized hyperparameter search scored by ROC-AUC against the held-out label (search, not training, is allowed to see labels — this is standard practice for model *selection* and does not constitute label leakage into the unsupervised fit).

## 7. Model Comparison & Evaluation

`scripts/evaluate.py` produces `reports/metrics.json` and `reports/model_comparison.csv`, comparing every model on:

- Training time / prediction time (throughput)
- ROC-AUC and Average Precision against `Is Fraud?` (evaluation only)
- Precision@k / Recall@k for k ∈ {50, 100, 500} (operationally, how many of the top-k flagged transactions an analyst reviews are real fraud)
- Number of anomalies flagged
- Qualitative: ease of implementation, computational cost, strengths/weaknesses, business usefulness

**Results are written by running the pipeline** (`python scripts/run_pipeline.py`) — see [Installation](#8-installation) below. This README references `reports/metrics.json` rather than hard-coding numbers so the reported results are always the actual output of the current codebase and dataset sample, not fabricated figures.

## 8. Installation

```bash
git clone <your-repo-url>
cd transaction-anomaly-detection

python3 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate

pip install -r requirements.txt
```

Download the dataset from Kaggle and place the CSV at the path configured in `configs/config.yaml` (`paths.raw_data`, default `data/raw/credit_card_transactions.csv`):

```bash
kaggle datasets download -d ealtman2019/credit-card-transactions -p data/raw --unzip
```

Run the full pipeline end-to-end:

```bash
python scripts/run_pipeline.py          # preprocess -> engineer features -> train -> evaluate
```

Or run stages individually:

```bash
python scripts/train.py                 # train & persist all models
python scripts/evaluate.py               # evaluate & compare all models
python scripts/predict.py --input data/raw/sample.csv --model isolation_forest
```

Launch the dashboard:

```bash
streamlit run dashboard/app.py
```

Run the test suite:

```bash
pytest tests/ -v --cov=src
```

## 10. Software Engineering Practices

- **Config-driven:** no file path or hyperparameter is hard-coded; everything lives in `configs/*.yaml` and is loaded through `src/utils/config.py`.
- **Logging:** every module logs through `src/utils/logger.py` (console + rotating file handler), never `print()`.
- **Reusability:** preprocessing, feature engineering, and models are all fit-once/reused via persisted artifacts (`models/*.pkl`, `models/*.pt`) with a common inference path shared by `scripts/predict.py` and the dashboard.
- **Testing:** unit tests for preprocessing, feature engineering, each model wrapper, and full pipeline integration (`tests/`).
- **Exception handling:** data loading/validation and model inference paths validate inputs and raise/log descriptive errors rather than failing silently.
